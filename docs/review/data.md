# Provider, data integrity, and schema review

Reviewed the provider discovery and profile pipelines, GitHub REST and GraphQL client behavior, and SQLite startup at `ee17bd96750c1a6deaa6f50d9b1ba8055b7c8fee` for `gh-migrate-dashboard-b0x.3`. The review identified three P1 findings, eight P2 findings, and one P3 finding. No P0 was established within the reviewed scope.

## Observations and request behavior

- Shared inventory parsers enforce provider and namespace identity, unique projects, and coherent exact, lower-bound, and unavailable observations. GitLab and Bitbucket inventory preserve absent storage figures as unavailable. Their inventory rollups retain lower bounds when only some projects report values. GitHub requires core repository counts and size data and stores unavailable optional repository REST signals as null. The findings above identify the exceptions.
- GitHub has throttling handlers for primary and secondary limits with a three-retry cap and a separate Octokit retry policy for eligible errors. GraphQL readiness batches split on timeout-like failures. REST organization discovery enforces the 10,000-repository envelope. The installed SDK was inspected for retry and request-hook behavior.
- GitLab and Bitbucket each default to a 30-second per-attempt deadline, two read retries, an 8 MiB JSON response cap, and a 100-page pagination cap. Both count each fetch attempt and accept caller cancellation on the request and backoff. GitLab can retry transient response-body failures, and its archive download has separate byte and time bounds. The source clients use single-attempt export creation for ambiguous writes. The call limits bound individual operations, and a large profile can still fan out across thousands of projects.
